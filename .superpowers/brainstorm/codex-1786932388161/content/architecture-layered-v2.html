修正版：经典分层的 Go 单体

参考 admin_back_go 的 systemsetting 模块，保留可读骨架，去掉迁移期复杂度。

一条业务请求必须能从上到下顺着读完
Router
路径 · 中间件 · Handler 绑定
↓
Handler
绑定 Request DTO · 基础校验 · 调用 Service · 输出 Response DTO
↓
Service
业务规则 · 跨字段校验 · 权限内业务判断 · 事务编排
↓
Repository
查询 · 分页 · 锁 · 持久化 · 数据库错误映射
↓
Model → PostgreSQL
表映射 · 字段类型 · 关联，不承载查询方法和 HTTP 语义
模块内文件

可预测的位置

route.go · handler.go · service.go

repository.go · model.go

request.go · response.go

公共横切能力

只保留稳定事实

config · database · logger · middleware

response · apperror · pagination · validate

外部 SDK 放 infra，由 Service 显式依赖

从 systemsetting 继承

  • 模块内聚的七个核心文件
  • Service 不依赖 gin.Context
  • Handler 不访问数据库
  • Repository 不做业务决策
  • 请求、响应 DTO 分开

不带入新项目

  • Route Registry / HTTPContract / OpenAPI Bundle
  • 为旧系统兼容而存在的缓存与多平台桥
  • 每层重复的 nil 依赖兜底
  • 没有真实替代实现的预设接口
  • 大量迁移脚本和历史合同

准确说法：Router、Handler、Service、Repository 是四个行为层，Model 是领域/持久化结构；工程沟通中称为五层也没有问题。
