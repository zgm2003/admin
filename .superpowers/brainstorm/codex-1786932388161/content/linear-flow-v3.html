核心原则：数据流必须线性

任何业务接口都能从路由顺着读到数据库，出错后沿原路返回。

示例：POST /api/admin/users
1. Router
声明路径、登录、权限码、操作日志，绑定 Handler.Create
↓
2. Handler
ShouldBindJSON(CreateRequest) → 基础格式校验 → service.Create(ctx, request)
↓
3. Service
规范化输入 → 检查用户名规则/角色存在性 → 编排创建用户与角色关系
↓
4. Repository
查询唯一性 → GORM Transaction → INSERT users / user_roles
↓
5. Model / PostgreSQL
User、Role、UserRole 表映射与数据库约束
↓ 返回
Response
CreateResponse → 统一 envelope：code / data / msg
错误同样线性

不抛进黑盒

数据库错误 → Repository 归类

业务冲突 → Service 返回 AppError

Handler → 统一 Response 映射 HTTP

事务同样可追踪

不隐藏副作用

Service 决定事务业务边界

Repository 执行 GORM 事务细节

一个请求内没有事件总线和异步旁路

允许

  • Gin + GORM + PostgreSQL
  • 模块内 Request / Response DTO
  • 明确的 Auth / Permission / Audit 中间件
  • 小而稳定的 error / response / pagination / validate
  • 本地 Go、Vue、PostgreSQL 直接启动

禁止

  • Generic BaseService / BaseRepository
  • 反射式路由和权限注册
  • 代码生成合同、SDK 和运行时 Schema
  • Handler 访问 DB，Service 依赖 gin.Context
  • Redis、MQ、Worker、微服务的提前设计

AI 开发约束：AI 只能按这个模板补充模块；新增抽象必须证明它消除了真实重复，不能只因为“以后可能用到”。
