# Admin 未来菜单与架构基线

> 状态：已确认的项目方向与未来菜单模板。
>
> 本文不是功能 spec、实施计划或数据库种子。未开始建设的栏目不得提前写入菜单表，
> 不得创建占位页面、空接口、未来表或通用抽象。具体模块开始前仍需单独确认业务规则。

## 1. 项目定位

当前项目只建设 Admin 管理后台，专注管理员、权限、系统配置、运维和后台治理能力。

- 普通用户产品、AI 产品和其他业务产品使用独立项目，不在当前 Admin 中承载运行时业务。
- AI 不迁移老项目的重型自研模块。未来业务项目可直接接入独立开源 Agent 或 Harness，
  例如 Pi 或最终选定的 DeepSeek 相关方案。
- 支付、钱包、充值、资金流水和兑换码属于未来业务项目，不进入当前 Admin 的预设表、
  Go 包、API、权限、前端目录或菜单。
- 当前 Admin 不为尚未存在的业务项目预留 AI、支付或其他业务管理入口。未来确有后台治理
  需求时，根据真实业务 API 重新设计，不直接读取业务项目数据库。
- 功能和 UI 以老项目成熟实现为参考，架构、协议、数据模型和工程质量以当前项目规则为准。

## 2. 固定工程基调

后端普通数据库请求保持单向线性调用：

```text
router -> middleware -> handler -> service -> repository -> model -> PostgreSQL
```

前端 HTTP 请求保持单向线性调用：

```text
view -> api/<module>.ts -> utils/request.ts -> Go API
```

工程约束：

- 保持目录直观、调用显式，优先让中国开发者容易阅读和接手。
- 复用成熟页面结构、业务规则和稳定公共组件，不复制老项目的重型架构。
- 不引入 Manager、Factory、BaseService、BaseRepository、BaseModel、DI 容器或运行时注册器。
- 公共组件只在多个真实页面出现稳定重复后抽取，不为未来假设创建万能组件。
- PostgreSQL、严格 DTO、显式错误、`TIMESTAMPTZ`、`deleted_at` 和统一 Yes/No 语义保持不变。

## 3. 已确认服务边界

### 3.1 腾讯云 COS

- 当前只支持腾讯云 COS，不支持阿里云 OSS。
- 不建设多云 Provider、Driver、Adapter 或动态注册机制。
- 对象存储只封装 COS 的上传、访问、删除和签名等真实能力。
- 密钥不得通过 API 回显，也不得进入普通日志和操作日志正文。
- 上传采用服务端代理、预签名 URL 还是临时凭证，在 COS 模块立项时根据真实业务确认。

### 3.2 邮件

- 邮件是主要外部消息通道，也是管理员邀请和邮箱验证码能力的基础依赖。
- 预设范围包括腾讯云邮件配置、模板元数据、发送日志和测试发送。
- 邮件正文以腾讯云模板为权威事实，Admin 不重复维护另一套正文。
- 邮件发送失败必须显式记录和返回，不得自动切换短信或伪造发送成功。

### 3.3 短信

- 短信需要建设，但属于次要通道。
- 短信接入受资质、签名和模板审核限制，任何核心流程不得只依赖短信。
- 预设范围包括腾讯云短信配置、模板元数据、发送日志和测试发送。
- 用户资源增加手机号字段；当前不增加地区、国家区号或地理位置相关表。

### 3.4 站内通知与实时连接

- `notification` 负责站内通知事实，`mail` 和 `sms` 负责各自发送通道。
- `realtime` 只提供一个经过认证的 WebSocket 连接，通过明确事件类型推送消息。
- WebSocket 是传输通道，不保存权威业务状态；PostgreSQL 和 HTTP API 仍是事实来源。
- 不为每个模块各建一套 WebSocket，也不提前建设通用事件总线。

## 4. 管理员账号与登录基线

### 4.1 注册与创建

- Admin 不提供公共注册入口或自动注册行为。
- 第一个超级管理员继续由 `bootstrap-admin` 创建。
- 后续管理员只能由具备权限的管理员在用户管理中邀请创建。
- 邀请时填写管理员邮箱并分配角色，系统发送激活邮件。
- 被邀请管理员通过邮件完成激活和密码设置。
- 不存在的邮箱尝试登录时不得自动创建账号，并返回不泄露内部状态的统一错误。

### 4.2 登录方式

- 管理员身份以邮箱为主要登录标识。
- 激活后的管理员支持邮箱验证码登录。
- 设置密码后支持邮箱和密码登录。
- 短信不参与管理员首次激活，也不是管理员登录的必要依赖。
- 具体验证码频率、邀请有效期、重发、失效和安全审计规则在认证模块实施前单独确认。

### 4.3 管理员资料

- 用户资源保留用户名、邮箱，并增加手机号字段。
- 手机号作为管理员可选资料；是否唯一、是否验证以及修改后的会话处理在个人中心实施前确认。
- 当前不建设省市区、经纬度、详细地址或行政区划表。

## 5. 个人中心基线

个人中心属于 Admin 自身能力，但不进入左侧业务菜单。入口固定放在侧栏底部头像区域。

预设内容：

- 个人资料和头像；
- 邮箱与手机号；
- 设置或修改密码；
- 查看和撤销自己的会话；
- 查看自己的登录记录；
- 退出登录。

个人中心只操作当前管理员自身数据。全局用户、会话和日志治理继续由有权限的管理页面负责。

## 6. Admin UI 壳层基线

### 6.1 侧栏与 Header

- 参考老项目的信息结构，将头像、用户名、角色、个人中心和退出入口放到侧栏底部。
- 侧栏折叠时账户区域只显示头像，不挤占菜单空间。
- Header 保留但保持精简：桌面约 `52px`，移动端约 `48px`。
- Header 只承担菜单开关、面包屑、语言和主题设置等全局工具，不再展示完整账户操作区。
- 移动端使用侧栏 Drawer，账户入口随侧栏一起展示。

### 6.2 主题设置

- 参考老项目主题抽屉的分组、模式选择、色板密度和操作层次。
- 保留亮色、暗色、主题色、界面显示、菜单行为、页面过渡和恢复默认设置。
- 主题变量使用清晰的语义 Token，但不建设多套布局引擎或动态主题插件系统。
- Admin 保持安静、紧凑、适合重复工作的视觉风格，不照搬无业务价值的渐变、装饰和大圆角。

### 6.3 RouterTabs 全屏

- 内容全屏只隐藏侧栏、Header 和 Footer，RouterTabs 必须始终可见。
- 全屏时在 RouterTabs 右端直接显示退出全屏按钮，不把唯一恢复入口藏在下拉菜单中。
- 同时支持 `Escape` 退出内容全屏。
- 全屏期间不得通过主题设置隐藏 RouterTabs。
- 当前源码和单元测试已声明全屏保留 RouterTabs，但真实使用反馈与之冲突；实施时必须先用浏览器
  复现，再修正实际状态或渲染问题，并增加浏览器级回归验证。

## 7. 未来菜单模板

| --- | --- |
| 已有 | 当前项目已经具备对应页面和权限 |

| 候选 | 老项目已有，但必须出现真实管理需求后再立项 |

├─ 菜单管理                                      已有
├─ 角色管理                                      已有
└─ 认证平台                                      已有

消息服务
├─ 站内通知                                      已确认未来
├─ 邮件服务                                      已确认未来；主要通道

菜单约束：

- 页面内部配置、模板、日志使用标签页或分区组织，不为每个操作制造多层菜单。
- 测试发送、连接检查、重置配置等是页面操作，不单独占菜单项。
- WebSocket、Redis、Queue 等技术能力不是用户菜单。
- AI、支付、钱包和普通用户业务不出现在当前 Admin 菜单模板中。
- 候选栏目不创建占位菜单；模块真正可用后才写入菜单基础数据。

## 8. 暂不建设

- Admin 公共注册和未知邮箱自动注册；
- AI 运行时、模型供应商、智能体、知识库、工作流和聊天页面；
- 支付、钱包、充值、资金流水和兑换码；
- 阿里云 OSS 和多云存储抽象；
- 多邮件或多短信供应商抽象；
- 用户地理位置字段和行政区划表；
- 为未来业务预留的表、API、Go 包、前端目录、权限和占位菜单；
- 通用 Adapter、Provider 市场、事件总线或配置驱动页面引擎。

## 9. 模块启动流程

项目所有者指定下一个模块后，按以下顺序推进：

1. 按任务范围核对老前端或老后端对应实现；
2. 区分直接继承、适配迁移和明确替换的内容；
3. 确认业务规则、页面范围、权限码、数据表和失败行为；
4. 用户批准设计；
5. 编写当前模块 spec 和实施 plan；
6. 按失败测试、最小实现和风险匹配验证完成开发；
7. 模块真实可用后再加入菜单基础数据。

当前最适合优先处理的独立切片是 Admin UI 壳层：侧栏账户入口、精简 Header、主题抽屉和
RouterTabs 全屏恢复。该切片不涉及数据库或业务 API，可以先稳定系统的第一印象与日常操作体验。
