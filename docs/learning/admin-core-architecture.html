01 / DECISIONS

已经可以定下来的十条架构规则

这些规则把 AuthPlatform、RBAC、Token、消息通道和 C 端业务的责任边界固定下来。

1. 用户身份全局唯一

user_account 是人的主身份。邮箱、手机号和密码是凭据，不为每个前端复制用户。

2. AuthPlatform 是安全边界

它表示 admin、canvas 等客户端入口的登录、Token、设备/IP、会话和注册策略，不是租户。

3. Session 按平台隔离

同一用户可在多个平台持有不同 Session；Refresh Token 和缓存 key 都带平台维度。

4. PostgreSQL 是事实源

用户、策略、Session、角色、授权和配置均以 PostgreSQL 为准；Redis 只做加速与协调。

5. Redis 状态必须可证明

快照使用 schema、version、ready/invalidating 和 tokenized CAS，不能用进程旧值假成功。

6. 双 Token 分工明确

短期 Access JWT 放内存；长期 Refresh Token 只放 HttpOnly Cookie，数据库只存 HMAC。

7. 页面权限不等于 API 权限

:view 只负责进入页面；list/detail/write 每项都由后端同名 action 再校验。

8. 验证码策略归消息通道

邮箱 TTL 唯一来源是 message_mail_config.ttl_minutes；短信将拥有自己的通道 TTL。

9. 重发只是限流

默认 60 秒规则复用 Redis rate limiter；不新增 cooldown Store、状态机或第二套过期协议。

10. C 端领域授权另算

RBAC 判断“能不能做”，业务表的 user_id/tenant_id 判断“能不能操作这一行”。

核心判断：Admin 的身份、Session、权限骨架已经具备可复用价值；进入 C 端不是重写认证，而是完成身份生命周期、部署边界和规模化失效协议后复用它。

04 / AUTH PLATFORM

AuthPlatform：客户端安全策略，而不是租户

每个请求先确定平台，再用平台策略决定登录方式、Token TTL、Session 缓存、设备/IP 绑定、并发会话和注册。

admin

管理后台

email,password；Access 900 秒；Refresh 14 天；Session/Access cache 1800 秒；最多 1 Session；禁止注册。

canvas

当前 C 端预设

email,password；TTL 与 admin 相同；最多 1 Session；允许首次验证码登录自动注册。

phone

可配置但不可用

数据库可保存 phone，但 LoginConfig 会过滤；直接 phone 登录也会拒绝，直到真实 SMS channel 就绪。

公开登录配置链路

1
识别客户端强制单值 X-Auth-Platform 与 UUID X-Device-ID，提取可信代理后的 IP 和 User-Agent。
2
读取平台策略热路径读取 auth:policy:v2:<code>；missing 才 singleflight + 5 秒 token lock 回源 PostgreSQL。
3
按通道 readiness 过滤email 只有 Mail 配置、模板、限流策略都可用时才展示；phone 在 SMS 接入前不展示。
4
返回真实能力前端只渲染服务端返回的登录类型；配置失败显示错误和重试，不假设默认密码登录。
多前端缺口：当前只配置一个 CORS_ORIGIN，Auth 的 Origin 校验也是单值，Admin 前端固定发送平台 admin。目标应使用部署配置维护 Origin→Platform 精确映射；浏览器传入的平台 header 必须与来源匹配，不能只扩成“多个 Origin 都允许”。

策略更新协议

PostgreSQL auth_platform (authority) ├─ policy_version: every effective security policy change increments └─ transaction commit Redis auth:policy:v2:<code> ready(policyVersion=N, policy=...) → acquire tokenized mutation lease (30s, renew every 10s) invalidating(token=...) → commit database change to N+1 ready(policyVersion=N+1) by CAS token Rule: corrupt / Redis error / invalidating ⇒ explicit 503; never return stale process policy.

关闭某一种登录方式只阻止新登录，不撤销既有 Session；禁用整个平台则让当前策略不可用，应阻断该平台后续认证。

05 / TOKEN

双 Token、Session 与认证状态

Access Token 解决高频鉴权，Refresh Token 解决长期登录，PostgreSQL Session 与 Redis generations 解决撤销和跨实例一致性。

Access Token

短期 JWT

  • HS256，issuer 为 admin-api。
  • claims：uid、sid、platform、Session ver、iat/nbf/exp。
  • 前端仅保存在 Pinia 内存，不写 LocalStorage。
  • 每次业务请求仍校验平台策略与 Session authority，不是纯离线 JWT。
Refresh Token

长期随机令牌

  • 浏览器只通过 HttpOnly Cookie 持有，名字为 admin_refresh_<platform>。
  • Cookie Path 为 /api/v1/auth，SameSite=Lax，Secure 随 HTTPS 配置。
  • 数据库只存 HMAC-SHA256，不存明文。
  • 每次刷新原子轮换 Token，并递增同一 Session version；旧 Token 只能使用一次。

登录成功时序

1
认证凭据密码验证或验证码 Check → user decision → Consume。验证码只有正确且准备签发身份时才原子删除。
2
首次登录建档同一事务创建 user_account、空 user_profile、默认角色关系、Access version=1；唯一键竞争 requery winner。
3
创建 Session锁定用户的平台 Session 集合，执行 max_sessions，生成 Refresh Token HMAC，必要时撤销最旧会话。
4
发布 authority更新 auth:sessions-state:<platform>:<user> generation，再发布版本化 Session snapshot。
5
签发 Access JWT使用当前 AuthPlatform Access TTL；Refresh Token 进入 HttpOnly Cookie，响应只返回 Access Token 与秒数。

目标版本模型：把公共变化与个人变化拆开

platform access version (one row per auth platform) increments when menu shape, menu status, role status or role-menu grants affect that platform principal access version (current permission_access_version per user) increments only when this user's role assignments or account availability change snapshot identity platform + policyVersion + platformAccessVersion + userID + principalAccessVersion + schemaVersion Result role/menu update: O(number of affected platforms), not O(number of users) user-role update: O(1 user) readers lazily rebuild after a shared version change

这个演进不要求现在新增平台成员关系。角色仍可全局存在，实际权限仍由“该角色在当前平台的 grants”过滤。若 C 端未来有组织/租户，再单独设计 tenant membership，不能混进 AuthPlatform。

当前数据说明：registered_user 默认角色的现有授权之后由维护者调整。本书只保留“C 端开放前核对默认角色在 Canvas 的实际页面/action”这一上线检查，不把当前 seed 视为架构阻塞。

目标 SendCode 顺序

1
策略与 readiness读取平台策略；Mail readiness v2 返回 ready + ttlMinutes，当前真实配置为 5 分钟。
2
简单限流Mail Service 复用 business_email_minute=1/60s 等规则，超限返回 429/10007；Redis 故障返回 503/10006。
3
获得 delivery lease只防同账号同时调用供应商。建议 lease 至少覆盖 provider timeout + 清理余量；它不是重发冷却。
4
保存新 code 并发送Redis key 不含 PII；发送成功后新验证码生效且旧码失效。失败则只清理当前 owner 的内容。
5
返回两个不同语义expiresAt 是验证码 5 分钟到期；前端重发按钮的 60 秒状态应来自限流语义，不能拿 expiresAt 冒充。
当前实现偏差：Auth 仍把验证码 TTL 固定为 10 分钟，并在 Mail 的 5 分钟配置前覆盖模板、Redis 和响应；Auth Redis Store 允许 1–15 分钟，而 Mail 配置约束允许 1–60 分钟。另一个阻塞是 Put 拒绝覆盖任何未过期 code，使 60 秒后重发仍可能得到 503。下一轮代码改造必须同时修正这两点。
不做复杂冷却协议：重发就是限流。保留现有 redis_rate，不新增 cooldown key、Store、数据库字段或状态机。delivery lease、验证码 TTL、rate limit 三者分别只解决并发发送、凭据寿命和请求频率。

08 / SCALE

百万用户、多实例容量模型

百万用户不是要求每一步都无数据库，而是要求高频读可缓存、低频写不按全体用户放大、故障行为有界可观测。

所有核心协议的最低并发验证

双实例

至少两个 Service、两个 Redis client；不能用同一个对象模拟跨实例。

竞争条件

Refresh 单 winner、验证码单消费、首次注册唯一键 winner、旧 publisher/token 拒绝。

故障点

policy/readiness read、code Put/Consume、lease release、PostgreSQL identity/Session/log、provider timeout。

热点预算

显式断言 ready 热读 PostgreSQL 查询数为 0，missing 风暴回源数有界。

恢复

请求取消不取消同实例 waiter；补偿只用 WithoutCancel + hard timeout。

安全失败

依赖故障不能返回旧权限、旧 policy、假发送成功或空能力列表。
