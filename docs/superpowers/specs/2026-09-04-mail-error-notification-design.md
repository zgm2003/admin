# 邮件错误通知契约

## 目标

修复邮件收件规则拒绝被误判为权限拒绝、导致前端没有 `ElNotification` 的问题，并统一
认证失败、权限拒绝和业务拒绝的通知责任。

## 错误语义

### 认证失败（401）

- 受保护请求首次返回 401 时，客户端可以执行一次 token 刷新。
- 刷新期间的中间 401 不弹通知。
- 刷新成功后重试原请求，成功路径不弹通知。
- 刷新失败时，属于终态认证失败，弹一次通知并沿用现有登录状态清理与跳转。
- 重试后的原请求仍为 401 时，必须弹一次通知并继续 reject；本次不改变该路径现有认证回调和跳转行为。
- 登录接口自身返回 401 时，属于终态认证失败，弹一次通知；登录页面不得再次弹相同错误。

### 权限拒绝（403）

- 所有 HTTP 403 都是终态错误，必须由请求层触发一次 `ElNotification`。
- `10003` 只表示 RBAC 权限中间件拒绝，不得在请求层被静默。
- 请求层不负责把 403 转换成成功响应或吞掉错误；调用方仍收到 `ApiError`。

### 邮件业务拒绝（403）

- 黑名单、拒绝规则命中仍使用 HTTP 403，但不得复用权限错误码 `10003`。
- 邮件模块新增业务错误码 `18000`（`CodeRecipientDenied`）。
- 返回错误的消息键为 `mail.recipientDenied`。
- 中文文案为“收件邮箱被收件规则拒绝”，英文文案为“Recipient rejected by mail rule”。
- 该错误同样触发一次 `ElNotification`。

## 通知责任

- `web/src/utils/request.ts` 负责终态 HTTP/API 错误的通用通知。
- 页面只处理字段校验和必须内联展示的局部状态，不重复提示同一个 `ApiError`。
- 认证跳转由现有未登录处理器执行；其提示只能由认证终态处理路径负责一次。
- 本次不引入 403 路由页面或通用错误组件；直接请求的无权限反馈以通知和原始 `ApiError` 为准。

## 兼容性

- 权限中间件的 HTTP 状态、业务码 `10003` 和现有 i18n 保持不变，仅改变前端是否静默。
- 邮件允许发送、限流、收件规则 CRUD 和仓储错误包装行为不变。
- 不修改 Redis 限流 key、数据库结构或邮件发送流程。

## 验收矩阵

| 场景 | HTTP | 业务码 | 通知 | 其他行为 |
| --- | ---: | ---: | --- | --- |
| 受保护请求 401，刷新成功 | 401（中间态） | 10002 | 否 | 重试原请求 |
| 刷新终态失败 | 401 | 10002 | 是，一次 | 清理凭证并跳转登录 |
| 登录接口认证失败 | 401 | 10002 | 是，一次 | 页面不得重复提示 |
| 重试后仍认证失败 | 401 | 10002 | 是，一次 | 继续 reject，保持现有认证回调行为 |
| RBAC 无权限 | 403 | 10003 | 是，一次 | 请求继续 reject |
| 邮件收件规则拒绝 | 403 | 18000 | 是，一次 | 请求继续 reject |
| 其他 HTTP/API 错误 | 按响应 | 非零 | 是，一次 | 请求继续 reject |
